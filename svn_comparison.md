# Сравнение Git и SVN

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это просто файл с 40-символьным хешем коммита, на который она указывает. Создание ветки не копирует ни одного файла проекта: Git хранит все объекты (файлы, деревья, коммиты) в одном хранилище, а ветки лишь ссылаются на них. Поэтому `git branch` выполняется мгновенно и почти не занимает места, а переключение между ветками — локальная операция.

В SVN ветка — это копия каталога внутри репозитория (`svn copy trunk branches/feature`). Технически копия «ленивая» и на сервере не дублирует данные, но концептуально ветка живёт как отдельная директория на центральном сервере. Чтобы её создать или переключиться на неё, нужен доступ к серверу, а слияние веток исторически было болезненным: SVN долго не отслеживал, какие ревизии уже были слиты, и разработчику приходилось вручную указывать диапазоны. Из-за этого ветки в SVN создавали редко, а в Git — на каждую задачу.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

Нет. SVN — централизованная система: история хранится только на сервере, а у разработчика на машине лежит рабочая копия одной ревизии. Команда `svn commit` отправляет изменения на сервер и создаёт там новую ревизию. Без связи с сервером коммит невозможен — можно только редактировать файлы локально и посмотреть `svn diff` относительно базовой ревизии.

В Git у каждого разработчика полная копия репозитория со всей историей, поэтому `git commit` создаёт коммит локально, а сеть нужна только для `push` и `pull`.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

- **Большие бинарные файлы.** Git хранит полную историю у каждого разработчика, и репозиторий с гигабайтами ассетов (игры, CAD, дизайн) становится неподъёмным. В SVN на машину выкачивается только рабочая копия нужной ревизии.
- **Частичное скачивание репозитория.** В SVN можно сделать checkout одной поддиректории монорепозитория. В Git полноценный аналог (sparse checkout) появился поздно и менее удобен.
- **Блокировка файлов.** `svn lock` позволяет монопольно захватить файл, который нельзя слить автоматически (например, `.psd` или `.docx`). В Git такого нет без внешних инструментов вроде Git LFS.
- **Строгий централизованный контроль доступа.** В SVN права можно задать на уровне отдельных каталогов, и история существует в единственном экземпляре на сервере — это удобно для корпоративных и регулируемых сред.
- **Простая линейная история и низкий порог входа.** Для небольших команд, которым не нужны ветки и распределённая работа, модель SVN «обновился — закоммитил» проще, чем staging, локальные ветки и rebase в Git.
